# Dia 3: tenant-service, outbox e isolamento por tenant

**Objetivo do dia (plano):** primeiro serviço de negócio (Tenants), com a base que todos os outros
vão usar: contexto de tenant por requisição, outbox transacional para o Pulsar e consumo
idempotente. No frontend, a aba "Tenants" com cadastro e lista.

## Decisões e por quê

- **Biblioteca comum em vez de copiar código.** Filtro de tenant, outbox e idempotência são iguais
  nos quatro serviços. Uma autoconfiguração (`META-INF/spring/...AutoConfiguration.imports`) faz o
  serviço ganhar tudo só por declarar a dependência, e os testes da biblioteca rodam uma vez.
- **Relay por polling** (ADR-0008). Change stream daria latência menor, mas exige guardar o resume
  token e tratar a perda dele. 200 ms no pior caso cabem na meta de p99 < 3 s.
- **Consulta antes de inserir, dentro da transação.** No MongoDB, uma chave duplicada dentro de uma
  transação aborta a transação inteira. Por isso `IdempotentConsumer` e o `POST` de tenants
  consultam antes; a chave única continua protegendo a corrida entre duas requisições.
- **Schema Avro próprio para o Pulsar** (`AvroBytesSchema`). O `Schema.NATIVE_AVRO` do cliente
  `pulsar-client-all` espera a classe Avro sombreada e rejeitava o schema dos contratos. O outbox
  guarda os bytes já serializados e o relay declara o schema ao Schema Registry do tópico, que
  aplica a compatibilidade FULL do namespace.
- **API de tenants fora do filtro de tenant.** Ela opera sobre o catálogo de tenants (plano
  administrativo, ADR-0005), então `/api/v1/tenants/**` fica nas exceções do filtro.
- **Concorrência otimista** (`@Version`): duas alterações simultâneas do mesmo tenant não se
  sobrepõem; a segunda recebe 409.

## Problemas encontrados no caminho

1. `@ConditionalOnBean` em configurações aninhadas não enxergava os beans do MongoDB, e o `Outbox`
   não era criado. Trocado por `@ConditionalOnClass`.
2. `Schema.NATIVE_AVRO` falhava com "The input schema is not of type 'org.apache.avro.Schema'"
   (Avro sombreado no cliente Pulsar). Resolvido com `AvroBytesSchema`.
3. Chave duplicada dentro da transação abortava o commit (`NoSuchTransaction`). Resolvido com a
   consulta antes de inserir.
4. Os testes de integração liam eventos de outros testes no mesmo tópico. As assinaturas passaram a
   começar em `Latest`, criadas antes da ação.
5. A JVM dos testes do tenant-service esperava 30 s para sair: o desligamento gracioso aguardava
   conexões keep-alive. No teste, o desligamento é imediato.
6. O workflow `tag-dia.yml` estava com YAML inválido (dois-pontos sem aspas na descrição dos
   inputs) e nunca rodou. Corrigido; as tags `dia-01` e `dia-02` são criadas depois do merge.

## Como testar

```bash
docker compose -f infra/docker-compose.yml up -d --build --wait

# Criar, consultar, alterar e listar
curl -s -X POST localhost:8081/api/v1/tenants -H 'Content-Type: application/json' \
  -d '{"id":"acme","nome":"ACME Ltda","plano":"PROFISSIONAL"}'
curl -s localhost:8081/api/v1/tenants/acme
curl -s -X PATCH localhost:8081/api/v1/tenants/acme -H 'Content-Type: application/json' \
  -d '{"nivelIsolamento":"SILO"}'
curl -s 'localhost:8081/api/v1/tenants?limite=10'

# O evento chegou ao Pulsar, com o schema registrado
curl -s localhost:8080/admin/v2/persistent/plataforma/tenants/tenant.criado.v1/stats | grep msgInCounter
curl -s localhost:8080/admin/v2/schemas/plataforma/tenants/tenant.criado.v1/schema

# Frontend: aba Tenants (proxy /api/v1/tenants → 8081)
cd frontend && npm run dev   # http://localhost:5173/#/tenants
```

Repita o primeiro `POST` para ver o 409 em Problem Details. Para ver a garantia do outbox, pare o
Pulsar (`docker compose -f infra/docker-compose.yml stop pulsar`), crie um tenant (a API responde
201 normalmente), suba o Pulsar de novo e confira que o evento sai sozinho.
