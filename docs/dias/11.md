## Decisões e por quê

- **Um chart só.** Um time, uma plataforma; os valores ficam num lugar e o chart sobe igual no kind
  e na homologação.
- **MongoDB e Pulsar de um nó, sem operadores.** Repetem o que o Compose já valida e cabem num kind
  do GitHub Actions; alta disponibilidade fica para depois.
- **Escalar pelo backlog, não por CPU.** O consumidor de pagamentos espera fila, não processador. O
  teste do CI cria backlog de verdade: pausa o consumidor, faz 60 pedidos e solta o KEDA.
- **Argo CD fora do CI.** Ele sincronizaria a `main`, não o PR. O CI valida os manifests; a
  instalação real fica para quando houver cluster permanente (decisão da VPS).
- **Claude Code Action só com segredo.** O repositório é público: sem a chave, nada roda e nada
  custa; com ela, só quem tem escrita aciona.

## Revisão do subagente arquiteto

O `arquiteto` aprovou o contrato (`runtime` opcional e compatível), o banco por serviço no chart, o
DNS do replica set e a JVM com raiz somente leitura. Pediu mudanças em 16 pontos; os que mudam o
comportamento:

1. **Sem NetworkPolicy, o Kubernetes furava a fronteira que o Compose tinha:** qualquer pod
   chamaria um serviço com `X-Tenant-Id` e `X-Papeis` forjados, ou leria o MongoDB de outro
   serviço. Agora o namespace nega toda entrada e libera só os caminhos da arquitetura; o CI tenta
   entrar com um pod intruso.
2. **A porta de métricas do gateway (com nomes de tenants) ia junto se o Service virasse
   LoadBalancer.** Agora é um Service à parte, sempre interno.
3. **Senha do Keycloak em texto nos values.** Agora é um Secret gerado na instalação.
4. **O release publicava qualquer commit.** Agora exige commit da `main` com o CI verde e recusa
   sobrescrever imagem publicada; actions fixadas por SHA.
5. **As réplicas novas do KEDA ficariam ociosas:** o consumidor buscava 1000 mensagens adiantado e,
   em Key_Shared, elas não migram. Fila configurável (`receiver-queue-size`), 20 no
   pagamentos-service.
6. **O teste do KEDA dependia de a JVM demorar mais que o HPA.** Agora lê o `desiredReplicas` do
   HPA, usa 120 pedidos e polling de 5 s no kind, espera o backlog completo e confere pedidos
   CONFIRMADO no fim.
7. Argo CD: `SkipDryRunOnMissingResource` no `ScaledObject`, retry na raiz e um projeto só para a
   raiz, que só cria Applications.
8. Menores: o serviço espera o último passo do init do Pulsar; gateway travado em uma réplica
   (rate limit em memória); tópico e assinatura do KEDA conferidos contra o `EventCatalog`;
   seccomp `RuntimeDefault`, `sizeLimit` no `/tmp` e PDB no pedidos-service.

Ficaram registrados, sem mudança agora: Keycloak em modo dev (sem Ingress até ter modo produção),
o nome do pod no `/api/status` público (baixo risco) e a volta do Pulsar standalone com volume
depois de trocar de IP, para os testes de caos (Dia 19).

## Como testar

```bash
kind create cluster --name plataforma
docker compose -f infra/docker-compose.yml build
for s in gateway status-service tenant-service catalogo-service pedidos-service pagamentos-service; do
  kind load docker-image plataforma/$s:dev --name plataforma
done
helm repo add kedacore https://kedacore.github.io/charts
helm install keda kedacore/keda --version 2.17.2 -n keda --create-namespace --wait
helm install plataforma deploy/helm/plataforma -n plataforma --create-namespace \
  -f deploy/helm/plataforma/values-kind.yaml --wait --timeout 15m
helm test plataforma -n plataforma --logs

kubectl -n plataforma port-forward svc/gateway 8000:8000 &
kubectl -n plataforma port-forward svc/keycloak 8180:8080 &
curl -s localhost:8000/api/status | jq '.status, .runtime'
infra/seed.sh
kubectl -n plataforma get scaledobject,hpa,pods
```

Com o port-forward de pé, o frontend com API real (`cd frontend && npm run dev`) funciona igual ao
Compose, e a página inicial mostra "Kubernetes · namespace plataforma · pod status-service-…".

## Recursos do Claude Code usados

| Recurso | Como foi usado | O que se aprende |
|---|---|---|
| Subagente em background | Frontend a partir do contrato `runtime`, em paralelo ao chart | Contrato primeiro destrava o paralelo |
| Subagente `arquiteto` | Revisão do chart, do Argo CD e dos workflows antes de sair do rascunho | Problema de arquitetura antes do merge |
| PR em rascunho como laboratório | O kind não sobe no ambiente do Claude; o job do CI é o cluster de teste | Usar o CI como ambiente quando o local não tem o recurso |
| Claude Code Action | `claude.yml`: `@claude` em issues e PRs | O Claude no próprio GitHub, com custo só quando ligado |
| `/code-review` | Revisão do PR | Segunda opinião automática |
