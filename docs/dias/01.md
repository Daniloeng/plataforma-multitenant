## Decisões e por quê

- **Um `status-service` já no Dia 1.** O plano pedia uma página de status; para ela mostrar algo
  real localmente, alguém precisa perguntar ao MongoDB e ao Pulsar se estão vivos. Um serviço
  pequeno faz isso e já estabelece o padrão dos próximos (Spring Boot, Testcontainers, JaCoCo,
  Dockerfile, healthcheck). No Dia 10 ele pode virar parte da página de saúde.
- **Verificações em paralelo com virtual threads.** O tempo de resposta passa a ser o da verificação
  mais lenta, não a soma; cada uma tem timeout de 2 s, então um componente fora do ar não segura a
  página. A API sempre responde 200 e o estado vem no corpo (`UP`, `DEGRADED`, `DOWN`).
- **Replica set de um nó em cada MongoDB, cada um com nome próprio** (`rs-tenants`, `rs-catalogo`...).
  Transações e change streams (usados pelo outbox no Dia 3) exigem replica set. Nomes e hosts
  distintos garantem que um driver nunca seja redirecionado ao banco de outro serviço. O healthcheck
  do Compose inicia o replica set na primeira subida. Do host, use `?directConnection=true`.
- **Namespaces Pulsar criados pela API REST de admin** (`curl`), em ~1 s, em vez do `pulsar-admin`,
  que abre uma JVM por comando e levava mais de 1 minuto. O status-service só sobe depois disso.
- **Pulsar standalone sem functions worker** e com heap de 512 MB, para caber no notebook.
- **Testes de integração no mesmo `mvn verify`** (`*IT` incluídos no Surefire), para a cobertura do
  JaCoCo contar os dois tipos e o comando ser um só.
- **`platform-core` sem Spring.** Tipos de domínio puros ficam testáveis e reaproveitáveis pela
  biblioteca de tenant context do Dia 3.

## Como testar

```bash
# 1. Ambiente completo (≈ 30 s depois das imagens baixadas)
docker compose -f infra/docker-compose.yml up -d --build --wait
curl -s localhost:8090/api/status | jq

# 2. Frontend contra a API real
cd frontend && npm ci && npm run dev        # http://localhost:5173

# 3. Derrubar um MongoDB e ver a plataforma "Degradada"
docker compose -f infra/docker-compose.yml stop mongo-pedidos

# 4. Testes
mvn -B verify
cd frontend && npm run test:coverage
```

Sem Docker, o modo demo mostra a mesma página com dados simulados:
`cd frontend && VITE_DEMO=true npm run dev`, ou a versão publicada no GitHub Pages.

## Achados do code review (todos corrigidos no PR)

1. Os 4 MongoDB tinham o mesmo replica set (`rs0`) e o mesmo host anunciado: um cliente sem
   `directConnection` podia cair no banco de outro serviço. Agora cada um tem nome e host próprios.
2. O job do Compose podia checar os namespaces antes do `pulsar-init` terminar. O status-service
   passou a depender do init concluído.
3. A mensagem completa de uma exceção inesperada ia para a resposta pública. Agora só o tipo vai
   para a API, e o detalhe vai para o log.
4. `StatusService.close()` parava na primeira falha; agora fecha todas e anexa as demais falhas.
5. O `HttpClient` do `PulsarCheck` não era fechado; agora é.
6. O frontend validava a lista de componentes, mas não cada item; agora valida.
7. Chave React dos cards passou a combinar índice e nome.
8. O modo demo mostrava detalhes diferentes dos reais; agora são iguais.
9. O deploy do Pages roda typecheck e testes antes do build.
10. Regra de nomes do `CLAUDE.md` esclarecida: código de produção em inglês; testes podem ter
    nomes em português, para lerem como especificação.
