## Decisões e por quê

- **Um `status-service` já no Dia 1.** O plano pedia uma página de status; para ela mostrar algo
  real localmente, alguém precisa perguntar ao MongoDB e ao Pulsar se estão vivos. Um serviço
  pequeno faz isso e já estabelece o padrão dos próximos (Spring Boot, Testcontainers, JaCoCo,
  Dockerfile, healthcheck). No Dia 10 ele pode virar parte da página de saúde.
- **Verificações em paralelo com virtual threads.** O tempo de resposta passa a ser o da verificação
  mais lenta, não a soma; cada uma tem timeout de 2 s, então um componente fora do ar não segura a
  página. A API sempre responde 200 e o estado vem no corpo (`UP`, `DEGRADED`, `DOWN`).
- **Replica set de um nó em cada MongoDB.** Transações e change streams (usados pelo outbox no Dia 3)
  exigem replica set. O healthcheck do Compose inicia o replica set na primeira subida.
- **Pulsar standalone sem functions worker** e com heap de 512 MB, para caber no notebook.
- **Testes de integração no mesmo `mvn verify`** (`*IT` incluídos no Surefire), para a cobertura do
  JaCoCo contar os dois tipos e o comando ser um só.
- **`platform-core` sem Spring.** Tipos de domínio puros ficam testáveis e reaproveitáveis pela
  biblioteca de tenant context do Dia 3.

## Como testar

```bash
# 1. Ambiente completo (≈ 30 s depois das imagens baixadas)
docker compose -f infra/docker-compose.yml up -d --build --wait
curl -s localhost:8090/api/status | jq

# 2. Frontend contra a API real
cd frontend && npm ci && npm run dev        # http://localhost:5173

# 3. Derrubar um MongoDB e ver a plataforma "Degradada"
docker compose -f infra/docker-compose.yml stop mongo-pedidos

# 4. Testes
mvn -B verify
cd frontend && npm run test:coverage
```

Sem Docker, o modo demo mostra a mesma página com dados simulados:
`cd frontend && VITE_DEMO=true npm run dev`, ou a versão publicada no GitHub Pages.

## Recursos do Claude Code usados

| Recurso | Como foi usado | O que se aprende |
|---|---|---|
| `CLAUDE.md` | Regras, estrutura e comandos do projeto, lidos por toda sessão futura | É a "memória de projeto": evita repetir contexto a cada dia |
| Hook `PostToolUse` | `.claude/hooks/format.sh` formata cada arquivo Java ou TS que o Claude edita | Hooks rodam no harness, não dependem do modelo lembrar; o CI continua sendo a garantia |
| Subagente em background | O frontend inteiro foi feito por um subagente enquanto o backend era escrito, com o contrato JSON de `/api/status` fixado antes | Paralelizar exige um contrato claro entre as partes |
| Plan mode / planejamento | O dia foi planejado a partir do plano de 22 dias antes de escrever código | Fixar escopo e contrato antes evita retrabalho |
| `/init` | Substituído por um `CLAUDE.md` escrito à mão, porque o repositório estava vazio | `/init` rende mais em código já existente |
